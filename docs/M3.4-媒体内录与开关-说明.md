## 一、真实人声的链路验证结果

检查对象：`session 45`（`classmate_20261115_124248`，真实人声 4 分 14 秒，经济学课）。

### 真实人声第一次成功触发了点名判定

```
12:47:02.365  ClassMate/QA: HIT rule=请同学回答 q=下面请同学回答一下编辑报酬低减规律是什么。
12:47:02.411  ClassMate/QA: card: 老师点名了 · 正在生成…
12:47:03.818  ClassMate/Llm: finish=stop reasoning_len=0 content_len=96 max_tokens=700
12:47:03.820  ClassMate/QA: answer ok latency_ms=1367 prompt_tokens=264 sentences=3
```

- 这是**第一次用真人说话（不是注入文本、不是回放 WAV）跑通全链路**：判定 → 振动 → 通知 → 上文 → 云端 → 3 点答案，**1367 ms**。
- `prompt_tokens=264` 说明上文确实带进去了（纯提问约 30–60 token）。
- `reasoning_len=0` 说明思考模式关住了，没有白烧 token。

### 发现 4 个问题，其中 1 个是最大的性能坑

| # | 问题 | 证据 | 处理 |
|---|------|------|---------|
| 1 | **停录后出稿要 82–94 秒**，还经常超时降级成抽取式垃圾标题（「然准时针时间的短」） | `stop->note=94075ms source=fallback`；`cloud llm call threw (timeout)` | **已修，见下节，现在 1.2 秒** |
| 2 | 会中增量批次**一次都没成功**，全是超时 | `增量待重试 seq=1（timeout）`×4 + `尾批未完成（TimeoutException）` | **已修**（同一个根因 + 关思考） |
| 3 | 点名命中后 0.4 秒即停止录音，答案差点丢掉 | HIT 12:47:02.365 → stop 12:47:02.713 → answer 12:47:03.820 | 未改行为，只记录 |
| 4 | 「回答」类长句仍有 1 条漏判 | 语料 `[长句内嵌] 9/10`：`前面那位同学回答得很好那么谁来讲一下第二步` | 漏判（不误报），暂不处理 |

### 最大的坑：分词器哈希写成 a XOR b，解析 merges 花了 80 秒

最初怀疑是网络慢、怀疑是思考模型，逐段加计时后才定位到真凶：

```
修复前： ClassMate/Tok: vocab 151643 entries 55ms
         ClassMate/Tok: merges 151387 pairs 80349ms   ← 80 秒！
修复后： ClassMate/Tok: merges 151387 pairs 165ms     ← 快了 487 倍
         停录→出稿：82474ms → 1161ms
```

根因在 `core/src/tokenizer.c`：pair 哈希写成 `(uint32_t)(key ^ (key >> 32))`，等价于
`左 id XOR 右 id`。token id 集中在 0–15 万，`a^b` 只有 17 位熵、撞值极多，
15 万条 merges 插进哈希表时全挤成一条长链，退化成平方级。换成 murmur3 finalizer 混匀即解。

**这件事的教训**：日志里「云端慢」不一定真是云端慢。加了 `ttfb/total` 分段计时后看到
HTTP 只占 1.5 秒，剩下 80 秒全在本地 C 代码里。遇到「出稿慢」先看 `ClassMate/Tok` 和 `ClassMate/Note` 两行。

## 二、三个新功能

### 1 + 2. 媒体内录 + 三档音频来源

设置区（点右上角「设置」展开）多了一行：

```
○ 线下声音    ● 媒体音频    ○ 两者一起
☑ 自动识别提问并生成答案
```

| 模式 | 录什么 | 需要什么 | 典型场景 |
|------|--------|----------|----------|
| 线下声音（默认） | 麦克风 | 录音权限 | 教室上课 |
| 媒体音频 | 手机**正在播放**的声音（内录） | 每次开录要过一次系统授权 | 网课、B 站、线上会议回放 |
| 两者一起 | 麦克风 + 媒体，软件混音 | 同上 | 直播课（老师声音从扬声器出来 + 现场同学发言） |

**媒体音频与线下声音完全同一套能力**：实时字幕、章节、笔记、套话判定、3 点答案，走的是
同一条 16 kHz PCM 管道（`AudioInput` 统一输出，`nativeFeed` 一行没改）。

选「媒体音频」或「两者一起」后按开始录音，会弹系统框：

```
要开始使用ClassMate录制或投放吗？   单个应用 / 取消 / 下一步
```

- 点「下一步」→「立即开始」即可；ColorOS / Android 16 等系统还支持**只录某一个 App**，
  想只录腾讯会议或只录浏览器，选「单个应用」更干净。
- 这个框是 Android 的安全设计，**每次录音都要点一次，代码绕不过去**。
- 本应用不截屏、不录画面、不上传任何音视频，只用这次授权拿音频采集通道。

**内录的系统硬限制（不是 bug，改代码也没用，提前说清楚）**：

1. 目标 App 自己声明「不允许被采集」→ 只能录到静音（DRM 视频、部分银行/会议 App）；
2. **通话类音频（`USAGE_VOICE_COMMUNICATION`）系统不给录** → 微信语音通话、腾讯会议「语音模式」
   可能拿不到声音；视频播放、网课、B 站这类走 `USAGE_MEDIA` 的能录到；
3. 手机媒体音量调到 0 时，内录同样是静音；
4. 「两者一起」若用扬声器外放，麦克风会**同时**收到一遍媒体声，字幕可能重复、判定也可能重复触发。
   要么戴耳机，要么这种场景选「媒体音频」单路。

为防「以为在录、其实静音」，实现里有两道自检：30 秒还没采到有效音量会在界面提示
「内录还没采到声音：检查媒体音量、或该 App 不允许被录制」；打不开采集时也会明确报错，不会静默录出空场次。

### 3. 自动识别提问并生成答案（默认开，可关）

- 默认**开启**，与之前行为一致。
- 关掉后：**只出字幕和章节、不判定、不振动、不弹卡片、不调云端**（一个 token 都不花）。
- 建议：看学习视频、听讲座这类「不会被点名」的场景关掉，省额度也省打扰。
- 已验证：关掉后注入「有没有同学回答一下这个问题」→ 日志无 `HIT`、无卡片；
  重新打开 → `HIT rule=谁来回答一下`，1173 ms 出 3 点答案。

## 四、用 adb 复现（不需要点界面）

```bash
# 线下声音录 30 秒（自动开始/停止，不需要点按钮）
adb shell am start -f 0x20000000 -n com.classmate.app/.MainActivity --es start_record mic
adb shell am start -f 0x20000000 -n com.classmate.app/.MainActivity --ez stop_record true

# 媒体内录 / 混音（会弹系统授权框，仍需人工点一次）
adb shell am start -f 0x20000000 -n com.classmate.app/.MainActivity --es start_record playback
adb shell am start -f 0x20000000 -n com.classmate.app/.MainActivity --es start_record both

# 查看耗时三段（关键排障日志）
adb logcat | grep -E "ClassMate/(Tok|Note|Llm|QA|Audio)"

# 关键指标含义
#   ClassMate/Tok : vocab/merges 解析耗时（正常 <300ms）
#   ClassMate/Note: t=+xxxms tokenizer / counted / llm call start|end
#   ClassMate/Llm : ttfb=首字节  total=整请求  reasoning_len(content_len)
#   ClassMate/QA  : HIT / answer ok latency_ms
```
